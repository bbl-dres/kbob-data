What is the KBOB Data Dictionary?

The KBOB (Coordination Conference for Public Sector Construction and Property Services) has represented the public building owners of the Confederation, the cantons, cities and municipalities since 1968; the Federal Office for Buildings and Logistics FOBL chairs it and hosts its secretariat. Its tasks include digital methods in construction (BIM) and the standardisation of property management.

The KBOB Data Dictionary captures existing data catalogues from the planning, construction and operation of built assets in a structured way, improves their quality and publishes them in machine-readable form. For every object type (building, room, bridge, luminaire, document type …) it records which attributes the type carries — with data type, unit, allowed values, property set and, where available, the counterpart in the open exchange format IFC. The structure follows ISO 23386, ISO 23387 and ISO 12006 and the DCAT metadata vocabulary.

The catalogues are captured in Excel workbooks, validated automatically and converted to RDF (repositories under Sources and links). This application reads the result from LINDAS and presents it as a reference work — it does not change the data.

What is a data dictionary?

The national glossary of Bauen digital Schweiz / buildingSMART Switzerland defines a data dictionary as a “centralised repository of information about data, such as meaning, relationships to other data, origin, usage and format”. A data dictionary therefore does not describe an individual building; it defines how buildings are described: which terms exist, what they mean and in which form their values are exchanged.

Why is it needed?

Data is abundant in the construction and real-estate industry, but differing terms, structures and systems make its end-to-end use difficult. A shared data language is the foundation for interoperable and reusable data. On 15 September 2026, Bauen digital Schweiz and buildingSMART Switzerland, together with bauenschweiz, SBV, infrasuisse, IFMA, KBOB, SIA and CRB, launch the recommendation “Data Dictionaries — no digital construction industry without a shared data language”.

Which standards apply?

SN EN ISO 23386:2020 (“Methodology to describe, author and maintain properties in interconnected data dictionaries”) defines how properties are defined, described by attributes, reviewed by experts and linked between data dictionaries. ISO 23387 describes data templates for construction objects, ISO 12006-3 the object-oriented framework for such dictionaries.

And the buildingSMART Data Dictionary?

The bSDD is buildingSMART’s international service in which classifications, properties and allowed values are published according to ISO 12006-3 and ISO 23386 and can be referenced from IFC models or IDS specifications. The KBOB Data Dictionary is a national dictionary of the same kind; its IFC mappings (IFC class and IFC property set) bridge to the definitions published there.

Terms used in this application

Object type
A class of things being described — a building, a room, a building element, a lighting installation or a document type. Every object type belongs to exactly one catalogue.
Catalogue
The source an object type comes from (for example “KBOB Data Dictionary FM” or “KBOB Dokumenttypenkatalog”). The catalogue is a filter, not a navigation level.
Attribute
A property an object type carries — room area, fire-resistance class, manufacturer. The national glossary uses “Merkmal” as the technical term (SIA 2051, SN EN ISO 23386); “Attribut” there denotes the data element that describes such a property in machine-interpretable form.
Property set
A named group of attributes (for example “KBOB_Geometry”). Where a property set corresponds to an IFC property set (“Pset_…”, “Qto_…”), the application shows both.
Data type
Text, number, integer, yes/no or date/time. A text attribute with a value list appears as Selection.
Unit and allowed values
The unit of measurement of a numeric attribute (m, m², kW …) or the list of values a selection attribute may take.
Maturity
The status of an entry in the catalogue: Candidate (in preparation) or Preview (released for preview). No entry is adopted yet.
LOIN milestone
The point in the life cycle at which an attribute should be available (level of information need according to SN EN 17412-1). The catalogue uses the values LZP1 to LZP9; their binding definition is still pending with the data publishers. Only a few attributes carry a milestone so far.
IRI
The permanent address of an entry in LINDAS (permalink), which can be copied and referenced in other systems.

What are LINDAS and I14Y?

LINDAS (Linked Data Services) is the linked-data service of the Swiss Federal Archives. Authorities publish data through it as knowledge graphs in RDF; the data can be queried with the query language SPARQL. This application sends such queries to LINDAS on every visit — it keeps no copy of the catalogue of its own. The wording of the queries can be inspected in the “Connection and query” dialog.

The catalogue currently lives on the LINDAS integration environment (int.lindas.admin.ch) in the named graph https://lindas.admin.ch/fobl/kbob/dd-fm. This is a preliminary release: content may change without notice.

I14Y is the Swiss Confederation’s interoperability platform, operated by the Federal Statistical Office. It lists the administration’s datasets and interfaces with their metadata — including the SPARQL service of the KBOB Data Dictionary. The data itself stays in LINDAS.

How is the data model built?

The “NatDD core” vocabulary (National Data Dictionary, version 0.1.0, Public Review Draft) describes a catalogue as a chain: a data dictionary contains classes (object types) and properties; a data template assigns a class its property requirements, and every requirement refers to a property, a group of properties (property set) and, where applicable, an enumeration scheme. A property is thus defined once and can be used in several object types with a different context.

This application condenses the chain, per object type, into one row per attribute and property set. The full description of the model, the namespaces and the queries is in the documentation Data model and SPARQL guide.

How do I use the application?

Search and filter
The search field searches names and descriptions of the current level. The Catalogue, Maturity and LOIN milestone fields narrow the list; “or” applies within a field, “and” between fields. Active filters appear as chips above the list and can be removed there one by one.
Views
List shows all details as a table with sortable columns. Gallery shows the same entries as cards — useful for document types, where the description is the main content. Graph shows on the overview which object types share property sets and, for an object type, its attributes grouped by property set.
Opening an object type or attribute
Clicking a name opens the next level. The breadcrumb above the title leads back; the browser’s back button works too, because every view has its own address and can be shared as a link.
Operating the graph
Dragging pans, the mouse wheel with Ctrl/Cmd or the buttons zoom, clicking a node opens its details in a side panel. With the keyboard: Tab from node to node, arrow keys pan, + and − zoom, 0 resets the view. A complete text version is provided for screen readers.
Language
The choice at the top right (DE/FR/IT/EN) switches the interface and the catalogue labels. Where a translation is missing in the catalogue, the German or English version appears.
Export
“Export to Excel” saves all object types and attributes as an XLSX workbook with three sheets.
Connection and query
Shows the SPARQL queries used and allows the endpoint and graph to be changed — for a local instance, say, or a future production instance.

What the data does not say

  • The catalogue has no requirement level: all requirements are “included” (represented in the template). Whether an attribute is mandatory or optional cannot be read from it.
  • LOIN milestones are recorded for only a few attributes (all from the AG ATB iDSK pilot); their definition LZP1–LZP9 is not yet binding.
  • No entry is adopted — all object types are Candidate or Preview.
  • Labels exist predominantly in English and German; French and Italian are translated only in small part.
  • The data comes from the integration environment; production publication through I14Y is planned for 2026.
