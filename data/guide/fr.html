Qu’est-ce que le KBOB Data Dictionary ?

La KBOB (Conférence de coordination des services de la construction et des immeubles des maîtres d’ouvrage publics) représente depuis 1968 les maîtres d’ouvrage publics de la Confédération, des cantons, des villes et des communes ; l’Office fédéral des constructions et de la logistique OFCL en assure la présidence et le secrétariat. Ses tâches comprennent les méthodes numériques dans la construction (BIM) et la standardisation de la gestion immobilière.

Le KBOB Data Dictionary recense de manière structurée les catalogues de données existants issus de la planification, de la construction et de l’exploitation des ouvrages, en améliore la qualité et les publie sous une forme lisible par machine. Pour chaque type d’objet (bâtiment, local, pont, luminaire, type de document…), il consigne les attributs que celui-ci comporte — avec type de données, unité, valeurs admises, property set et, le cas échéant, la correspondance dans le format d’échange ouvert IFC. La structure suit les normes ISO 23386, ISO 23387 et ISO 12006 ainsi que le vocabulaire de métadonnées DCAT.

Les catalogues sont saisis dans des classeurs Excel, contrôlés automatiquement et convertis en RDF (dépôts sous Sources et liens). Cette application lit le résultat depuis LINDAS et le présente comme ouvrage de référence — elle ne modifie pas les données.

Qu’est-ce qu’un data dictionary ?

Le glossaire national de Bauen digital Schweiz / buildingSMART Switzerland définit le data dictionary (catalogue de données) comme un « dépôt centralisé d’informations sur les données, telles que leur signification, leurs relations avec d’autres données, leur origine, leur utilisation et leur format ». Un data dictionary ne décrit donc pas un ouvrage particulier : il fixe comment les ouvrages sont décrits — quels termes existent, ce qu’ils signifient et sous quelle forme leurs valeurs sont échangées.

Pourquoi en a-t-on besoin ?

Les données abondent dans l’économie de la construction et de l’immobilier ; mais des termes, des structures et des systèmes différents en compliquent l’utilisation continue. Un langage de données commun est la base de données interopérables et réutilisables. Bauen digital Schweiz et buildingSMART Switzerland lancent à cet effet, le 15 septembre 2026, avec bauenschweiz, la SSE, infrasuisse, IFMA, la KBOB, la SIA et le CRB, la recommandation « Data Dictionaries — sans langage de données commun, pas d’économie de la construction numérique ».

Quelles normes s’appliquent ?

SN EN ISO 23386:2020 (« Méthodologie de description, de création et de maintenance des propriétés dans des dictionnaires de données interconnectés ») fixe la manière dont les attributs sont définis, décrits par des attributs de description, vérifiés par des experts et reliés entre catalogues. ISO 23387 décrit les modèles de données (data templates) pour les objets de construction, ISO 12006-3 le cadre orienté objet de tels catalogues.

Et le buildingSMART Data Dictionary ?

Le bSDD est le service international de buildingSMART dans lequel des classifications, des attributs et des valeurs admises sont publiés selon ISO 12006-3 et ISO 23386 et peuvent être référencés depuis des modèles IFC ou des spécifications IDS. Le KBOB Data Dictionary est un catalogue national du même type ; ses correspondances IFC (classe IFC et property set IFC) font le lien avec les définitions qui y sont publiées.

Termes utilisés dans cette application

Type d’objet
Une classe de choses décrites — un bâtiment, un local, un élément de construction, une installation d’éclairage ou un type de document. Chaque type d’objet appartient à exactement un catalogue.
Catalogue
La source dont provient un type d’objet (par exemple « KBOB Data Dictionary FM » ou « KBOB Dokumenttypenkatalog »). Le catalogue est un filtre, pas un niveau de navigation.
Attribut
Une propriété que comporte un type d’objet — surface du local, classe de résistance au feu, fabricant. Le glossaire national utilise « Merkmal » comme terme technique (SIA 2051, SN EN ISO 23386) ; « Attribut » y désigne l’élément de données qui décrit une telle propriété de manière interprétable par machine.
Property set
Un groupe nommé d’attributs (par exemple « KBOB_Geometry »). Lorsqu’un property set correspond à un property set IFC (« Pset_… », « Qto_… »), l’application affiche les deux.
Type de données
Texte, nombre, nombre entier, oui/non ou date/heure. Un attribut de type texte doté d’une liste de valeurs apparaît comme Choix.
Unité et valeurs admises
L’unité de mesure d’un attribut numérique (m, m², kW…) ou la liste des valeurs qu’un attribut de type choix peut prendre.
Maturité
Le statut d’une entrée dans le catalogue : Candidate (en élaboration) ou Preview (libéré pour aperçu). Aucune entrée n’est adoptée pour l’instant.
Jalon LOIN
Le moment du cycle de vie auquel un attribut doit être disponible (niveau d’information requis selon SN EN 17412-1). Le catalogue utilise les valeurs LZP1 à LZP9 ; leur définition contraignante est encore attendue des éditeurs des données. Peu d’attributs portent pour l’instant un jalon.
IRI
L’adresse permanente d’une entrée dans LINDAS (permalien), que l’on peut copier et référencer dans d’autres systèmes.

Que sont LINDAS et I14Y ?

LINDAS (Linked Data Services) est le service de données liées des Archives fédérales suisses. Les autorités y publient des données sous forme de graphes de connaissances au format RDF ; les données peuvent être interrogées avec le langage de requête SPARQL. Cette application adresse de telles requêtes à LINDAS à chaque consultation — elle ne conserve aucune copie propre du catalogue. Le texte des requêtes est visible dans le dialogue « Connexion et requête ».

Le catalogue se trouve actuellement sur l’environnement d’intégration de LINDAS (int.lindas.admin.ch), dans le graphe nommé https://lindas.admin.ch/fobl/kbob/dd-fm. Il s’agit d’une version préliminaire : les contenus peuvent changer sans préavis.

I14Y est la plateforme d’interopérabilité de la Confédération, exploitée par l’Office fédéral de la statistique. Elle recense les jeux de données et les interfaces de l’administration avec leurs métadonnées — y compris le service SPARQL du KBOB Data Dictionary. Les données elles-mêmes restent dans LINDAS.

Comment le modèle de données est-il construit ?

Le vocabulaire « NatDD core » (National Data Dictionary, version 0.1.0, Public Review Draft) décrit un catalogue comme une chaîne : un data dictionary contient des classes (types d’objet) et des attributs ; un modèle de données (data template) associe à une classe ses exigences d’attributs, et chaque exigence renvoie à un attribut, à un groupe d’attributs (property set) et, le cas échéant, à un schéma de valeurs. Un attribut est ainsi défini une seule fois et peut être utilisé dans plusieurs types d’objet avec un contexte différent.

Cette application condense la chaîne, pour chaque type d’objet, en une ligne par attribut et property set. La description complète du modèle, des espaces de noms et des requêtes se trouve dans la documentation Modèle de données et guide SPARQL (en anglais).

Comment utiliser l’application ?

Rechercher et filtrer
Le champ de recherche parcourt les noms et les descriptions du niveau actuel. Les champs Catalogue, Maturité et Jalon LOIN restreignent la liste ; à l’intérieur d’un champ s’applique « ou », entre les champs « et ». Les filtres actifs apparaissent sous forme de puces au-dessus de la liste et peuvent y être retirés un à un.
Vues
Liste affiche toutes les indications sous forme de tableau à colonnes triables. Galerie affiche les mêmes entrées sous forme de cartes — utile pour les types de document, où la description est au premier plan. Graphe montre, dans la vue d’ensemble, quels types d’objet partagent des property sets et, pour un type d’objet, ses attributs groupés par property set.
Ouvrir un type d’objet ou un attribut
Un clic sur un nom ouvre le niveau suivant. Le fil d’Ariane au-dessus du titre permet de revenir en arrière ; le bouton Retour du navigateur fonctionne aussi, car chaque vue a sa propre adresse et peut être partagée comme lien.
Manipuler le graphe
Glisser déplace, la molette avec Ctrl/Cmd ou les boutons zooment, un clic sur un nœud ouvre ses indications dans un panneau latéral. Au clavier : Tab de nœud en nœud, les flèches déplacent, + et − zooment, 0 réinitialise le cadrage. Une version textuelle complète est disponible pour les lecteurs d’écran.
Langue
Le choix en haut à droite (DE/FR/IT/EN) change l’interface et les libellés du catalogue. Lorsqu’une traduction manque dans le catalogue, la version allemande ou anglaise apparaît.
Export
« Exporter vers Excel » enregistre tous les types d’objet et attributs dans un classeur XLSX à trois feuilles.
Connexion et requête
Affiche les requêtes SPARQL utilisées et permet de changer de point d’accès et de graphe — par exemple pour une instance locale ou une future instance de production.

Ce que les données ne disent pas

  • Le catalogue ne connaît aucun niveau d’obligation : toutes les exigences sont à « included » (représenté dans le modèle). On ne peut pas en déduire si un attribut est obligatoire ou facultatif.
  • Les jalons LOIN ne sont saisis que pour quelques attributs (tous issus du projet pilote AG ATB iDSK) ; leur définition LZP1–LZP9 n’est pas encore contraignante.
  • Aucune entrée n’est adoptée — tous les types d’objet sont à Candidate ou Preview.
  • Les libellés existent principalement en anglais et en allemand ; le français et l’italien ne sont traduits que pour une petite partie.
  • Les données proviennent de l’environnement d’intégration ; la publication de production via I14Y est prévue pour 2026.
